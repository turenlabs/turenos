Inbox + Library

Two zones with two distinct jobs: "what needs me" up top, "find anything" below.

  1. The inbox is a feed, not a nav. Compact tinted rows with status + age, an explicit Open action, and dismiss-on-read semantics. It answers "what needs me right now" and nothing else — no grouping, no expansion.
  2. Pins are first-class. Always-visible section near the top; users self-organize instead of hunting through trees.
  3. One canonical list, chronologically grouped. Every session appears here exactly once, newest first, with project as a tag — not a container. Filter chips replace the project tree and the Inactive/Archived disclosures; nothing is more than one click deep.

Data-model fixes this assumes

  • Single derived SessionNavStatus consumed by nav and session page alike.
  • projectID stored on the session record — no worktree/sandbox path inference.
  • Origin stored server-side instead of the ses_loop_ id prefix.

Trade-offs

  • Users scanning "everything in project X" must use the filter chip instead of a tree.
  • Needs the inbox to clear reliably or it becomes the second confusing list.

Activity feed

The simplest possible model: one list, everything in it, newest activity first.

  1. Filter chips are the entire nav model. Needs you / Running / Unread / Archived are lenses over the same list — not separate sections that can disagree with it. No groups appear or disappear under the user's cursor.
  2. Relative timestamps carry the chronology — no date headers needed when every row says its age. Status is always the left icon; project is always a right-side tag. Two columns of meaning, zero ambiguity.
  3. Pinned rows pin to the top of the list (with a pin glyph), inside the same list — still one place to look.

Data-model fixes this assumes

  • Same canonical status + stored projectID as option A.
  • List is driven by a single sorted projection — no merge of index + events + focused sync at render time.

Trade-offs

  • Long lists on busy days — leans hard on chips and ⌘K being genuinely good.
  • No project-centric view at all; users who think in projects lose that axis in the nav.

Project tree, deduped

Smallest departure from today: keep the tree, remove the second copy of everything.

  1. Status groups become a digest strip. "2 running · 1 needs you" pills summarize and filter/jump — they never render the sessions themselves, so nothing exists twice.
  2. Each session renders exactly once, under its project. Status rolls up onto collapsed project rows as badges (blue dot = running, ⚠ = needs you), so the signal survives a collapsed tree.
  3. Inactive / Archived get counts so users can see there's something behind the disclosure without opening it — and Archived moves to a per-project filter or a global view.

Data-model fixes this assumes

  • Same canonical status + stored projectID — this is what actually fixes "wrong project" reports.
  • Digest counts derive from the same projection as the rows, so the strip can never disagree with the tree.

Trade-offs

  • Keeps today's muscle memory — lowest migration cost.
  • Old sessions are still two clicks deep; "can't find things" improves least of the three.
